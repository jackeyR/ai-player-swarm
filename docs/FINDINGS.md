## F1 · 房间输入限流计数从未复位

**现象**　冒烟第一轮：`room_input_total = 44`，但 `room_input_rejected_total{code="rate_limited"} = 110`。
接受数远小于拒绝数，且随着运行时间推移几乎 100% 被拒。

**定位**　日志与代码对账：限流判定是 `p.inputsThisTick >= 2`，而 `inputsThisTick` 只在
`applyInputLocked` 里 `++`，全仓库搜不到任何清零。于是每个玩家累计打满 2 条输入后，永久处于被限流状态。

**根因**　「每 tick 配额」这类字段的生命周期必须跟着 tick 走。写的人默认「下一个 tick 会重置」，
但这个房间里根本没有 tick 级的重置点。

**修复与验证**　在 `Room.drainInputsLocked()` 开头统一清零所有玩家的 `inputsThisTick`。
修复后同样的冒烟负载下 `rate_limited` 归零，`room_input_total` 从 44 涨到 1100+，
`invalid_inputs`（真正该被拒的那一类）仍然被准确拦下 —— 说明限流与校验没有被一起放空。

**面试怎么讲**　「一个 2 行的 bug，但它让整条输入链路在 3 秒后彻底失效，而所有错误率指标看起来都『正常』——
因为被限流也是一种『成功响应』。这类问题只有对着『接受数 / 拒绝数』的比值做断言才拦得住。」

## F2 · bot 不发房间层心跳，5 秒后被踢

**现象**　`session_total{result="abandoned"} = 22 / 30`，`session_errors_total{code="heartbeat_timeout"} = 19`，
而客户端侧没有任何报错。

**定位**　服务端 `checkHeartbeatsLocked` 判定标准是「应用层多久没收到任何帧」，
超时阈值 5s。挂机 persona 的操作间隔是 9–20 秒，且 `ActionsPerMatch` 用完后不再发输入。
两端各自都「合理」，合起来就是：安静的玩家必然被踢。

**根因**　真实客户端有保活包，协议设计里也有房间层 ping/pong，但 bot 只对 gateway 发了心跳，
进房之后一条闲聊帧都不发。**bot 不发明人不会发的行为，也不能漏掉人会发的行为。**

**修复与验证**　`bot.play` 的输入循环里每 2 秒发一次 `RoomPing`（挂机分支也要发）。
修复后 `heartbeat_timeout` 归零，`abandoned` 从 22 降到 5（剩下的都是 persona 主动注入的
「结算前退出」），完成局数从 8 涨到 19。

**面试怎么讲**　「这是保真度问题，不是 bug 问题——服务端没错、客户端也没错，
错的是『我的 bot 有一个真实玩家不会有的行为：连上之后一声不吭』。」

## F3 · 结算帧与关连接存在写竞态

**现象**　端到端测试里 2 个 bot 在同一局里，一个记 `result=draw`、另一个记 `error_code=match_aborted`。
`stats.Matches` 只有 1，但 `Sessions` 是 2 —— **一局打完了却被记成中断**，goodput 直接被少算一半。

**定位**　`Room.finalize` 先 `sendImportant(结算帧)` 入队，紧接着 `Close()` 发 `RoomClose` 并
`p.close()` 关闭 socket。写循环是独立 goroutine，`close()` 关连接时队列里的结算帧可能还没写出去。
客户端侧同理：读循环先报 EOF，`select` 随机选中 `room.closed` 分支，把已到的结算当没发生。

**根因**　**「发出去」和「写进 socket」是两件事**。用有界队列做背压是对的，但把「决定成败的帧」
也丢进可丢队列里就是错的。这是压测工具的头号隐性 bug：只在负载高时偶发，且表现为「数字少了一点」。

**修复与验证**　两端各改一处：
- 服务端新增 `peer.sendSync`（共享写锁 + 同步 `WriteFrame`），结算帧与 `RoomClose` 改为同步写；
- 客户端在 `room.closed` 分支先补收一次结算帧（200ms 窗口）再判中断。

修复后端到端测试稳定 `Matches == 2`，连续跑 20 次无抖动。

**面试怎么讲**　「压测工具自己丢数据是最难发现的，因为它只表现为『吞吐比你预期的低一点』。
我给『必须送达』和『可丢弃』两类帧设计了两条写入路径，而不是靠调大队列长度。」

## F4 · 所有对局都是 0:0 平局

**现象**　冒烟 19 局，`matches_win = 0`、`matches_loss = 0`、`matches_draw = 19`。链路全绿，指标有数。

**定位**　三层叠加：
1. 两队出生点相距约 6667 单位，而移动速度是 15 单位/tick（10Hz ⇒ 1.5 m/s），一局 10 秒根本走不到一起；
2. persona 的「双峰操作间隔」间歇段是 3–10 秒，短对局里 bot 大部分时间在「走路看地图」；
3. bot 纯随机游走，不追人，靠近了也不会持续攻击。

**根因**　**压测跑通了，但胜负逻辑一行都没被执行到。** 这是「假通过」：所有断言都过，
报告也能出，可核心业务分支的覆盖率是 0。

**修复与验证**
- 出生点改到 45% / 55%，纵向间距收敛到地图的 ±1/5；
- `MaxMovePerTick` 15 → 40（10Hz 下 4 m/s，接近真人跑动）；
- 抽出 `protocol.AttackRange`（120）让客户端与服务端共用同一口径；
- bot 增加「看见敌人就追、进入命中半径就持续攻击」，追击时用爆发段节奏而非间歇段。

修复后冒烟 `matches_complete = 15`，`inputs_sent` 从 180 涨到 1124。
并在房间里补了白盒测试 `TestCombatProducesKills`，**只断言「跑完一局」是不够的，必须断言「打出了击杀」**。

**面试怎么讲**　「最容易骗过自己的指标是『对局完成数』——它只证明状态机走得通。
真正证明业务被覆盖的是『击杀数 > 0』。我后来把这条写进了端到端测试。」

## F5 · CO 修正把样本数放大了，报告自相矛盾

**现象**　`result.json` 里 `phase.match_start.count = 521`，但整轮只有 30 个 bot。
看起来像统计错了。

**定位**　HdrHistogram 的 `RecordWithExpectedInterval` 会按预期间隔**补记**样本：
一个 5 秒的响应在 200ms 的预期间隔下会补 25 个。这是 coordinated-omission 修正的本意，
但 `count` 因此不再是「观测次数」。报告里若直接写「521 次观测」，就是错的。

**根因**　把「修正后的样本量」当成「真实事件数」。两者含义不同，混用会同时误导读者和后面的自己。

**修复与验证**　`report.Reporter` 额外维护一套**真实观测计数**，输出到 `result.json` 的 `samples` 字段，
并在 `docs/METRICS.md` 明确写「两个数都要看」。同一份结果现在是：
`phase.match_start` 观测 30 次、修正后样本 523 个 —— 两个数字都自洽。

**面试怎么讲**　「CO 修正会让样本量膨胀，这是原理决定的。所以我同时输出修正前后的样本数，
报告里写『30 次真实观测，经 CO 修正后 523 个样本，p99 = 14.0s』。只报一个数都会让人误解。」

## F6 · 指标端点开关的语义歧义

**现象**　端到端测试想关掉指标端点，传 `MetricsAddr = ""`，结果还是去监听 `:9090` 并
`bind: Only one usage of each socket address` 失败（本机已经跑着一个 `sutd`）。

**定位**　`config.Defaults()` 把空字符串当成「没填」并填上默认端口 `:9090`，
于是「我要关掉」和「我没填」变成了同一件事。

**根因**　用同一个值表达两种意图。默认值填充函数无法区分「调用方明确要空」与「调用方没意见」。

**修复与验证**　引入显式哨兵 `sut.MetricsDisabled = "-"`，`Defaults()` 不再覆盖它，`Start()` 见到就跳过。
测试改用哨兵后可以与本机 `sutd` 并存运行。

**面试怎么讲**　「配置里最贵的 bug 不是写错值，是语义撞车。空字符串同时表示
『默认』和『关闭』这件事，在一个会跑在 CI 里的服务上迟早会炸。」

## F7 · `WaitGroup.Add` 写在派发出去的 goroutine 里

**现象**　`internal/runner` 的工件测试间歇性失败：3 个 bot 的结果文件里只有 2 条会话 + 1 条汇总。
`-count=5` 里有 3 次挂，`-count=1` 全过。典型的时序问题。

**定位**　调度器的写法是 `go fn(...)`，而 `fn` 里第一句才是 `wgBots.Add(1)`。
于是 `Dispatcher.Run` 返回后立刻执行的 `wgBots.Wait()` 可能在任何 `Add` 之前就看到计数为 0，
直接返回；随后 `cancel()` 取消上下文、关闭结果文件，那几个「刚要被调度」的 bot 才发现
自己被取消了，写结果时报 `writer closed` —— **写失败被 `if err != nil { counter++ }` 吞掉**。

**根因**　`WaitGroup` 的经典用法错误：`Add` 必须在 `go` 之前、在**调用方 goroutine** 里执行。
更深一层是调度器的接口设计问题：它把「决定并发」藏在了回调内部，调用方无法在派发时同步计数。

**修复与验证**　把 `Dispatcher.Run` 的契约改成**同步调用 spawn**：
调度器准时喊人、喊完不等待；是否起 goroutine 由 spawn 自己决定。
调用方于是可以在 spawn 里同步 `wg.Add(1)` 再 `go`。
同时把「写 run_summary 失败」从忽略改成返回错误——这类静默失败正是 bug 的温床。
`sched` 与 `runner` 各加一条断言，`-count=5` 稳定通过。

**面试怎么讲**　「这是 `WaitGroup` 的教科书坑，但它藏在一个看起来很优雅的回调接口后面。
修的时候我没有打补丁（在 Wait 前 sleep 一下），而是改了调度器的契约——
**让『谁负责并发』这件事在函数签名里就说明白**。」

## F8 · `result.json` 里装的是 YAML

**现象**　用 Python 读 `results/<run>/result.json`，`json.load` 直接报
`Expecting value: line 1 column 1`。

**定位**　`runner.writeJSON` 里写的是 `yaml.Marshal` —— 文件名叫 `.json`，内容是 YAML。
Go 侧读回来不报错（YAML 是 JSON 的超集），人眼扫一眼也「看起来像 JSON」，
所以整个 Go 测试套件都是绿的。

**根因**　**命名与格式是两个独立的事实，只有「让消费者真的按格式解析一次」才能对上。**
写文件的人和读文件的人之间没有任何编译期约束。

**修复与验证**　改用 `encoding/json`；并在 `internal/runner` 增加工件契约测试：
逐个文件用**对应的解析器**读一遍（`result.json`/`meta.json` 用 `json.Unmarshal`，
`plan.yaml` 用 `yaml.Unmarshal` 再反解回结构体比对，`bots.jsonl` 逐行 `json.Unmarshal`
并检查最后一行是 `run_summary`）。

**面试怎么讲**　「一个 'JSON' 文件在 Go 里能读、在 Python 里炸，因为 Go 的 YAML 库
能吃 JSON。所以我给每个产物都配了一条『用对的解析器读一遍』的测试——
这类 bug 单靠类型系统是拦不住的。」

# 第二轮：做真人客户端时发现的

这一轮的 6 个问题都来自「换一个消费者」：客户端不按 bot 的方式使用协议，
于是被 bot 与服务器共同掩盖的问题暴露了出来。这也是为什么要写真人客户端——
**同一套代码的两个消费者，比一套代码的一百次自测更能发现问题。**

## F9 · 真人客户端把打完的对局记成掉线

**现象**　两个客户端都打完了整局：服务端 `room_tick_total = 80`、`session_total{result="draw"} = 2`，
说明房间正常结算并给两个玩家都记了账。但客户端侧的 `bots.jsonl` 是 **0 字节**，
日志最后一行是「房间连接已断开（未收到结算）」。

**定位**　服务端 `finalize` 先 `sendSync(结算帧)` 再 `Close()`。两条消息几乎同时到达客户端，
`select` 里 `<-room.Closed()` 与 `<-room.Settles()` **同时就绪**，Go 随机选一个。
选中前者就把已打完的对局记成中断。

**根因**　这**正是 F3**，只不过换了个新写的消费者（`cmd/client`）。
当时的修法是在 bot 的 `play()` 里内联一段「关闭后补收一次结算」的 if——于是同样的坑
在新客户端里必然复现。**修在调用点的 bug 会随调用点增长而复活。**

**修复与验证**　把补收做成 API：`RoomSession.TrySettle()`（非阻塞取一次结算），
任何消费者在 `Closed` 分支里调它即可。客户端改为「先 TrySettle → 再等 200ms → 才认掉线」。
新增 `srv/sut/client_e2e_test.go`：两个客户端走公开 API 打同一局，
断言两者拿到**同一 tick、同一结果**的结算。

**面试怎么讲**　「同一个竞态我在 bot 里修过一次，写客户端时又踩了一遍。第二次我没有复制那段
if，而是把它变成 `TrySettle()` 这个方法——**修在调用点的 bug 会随调用点增长而复活，
修在接口上的不会**。」

## F10 · 计划指纹包含机器绝对路径

**现象**　同一份 `plans/smoke.yaml`，在仓库根目录跑和在别的机器上跑，`plan_fingerprint` 不一样，
于是「指纹相同 ⇔ 同一次实验」这个唯一用途直接失效。

**定位**　`cmd/runner` 读计划时会把 `sink.dir` / `catalog_file` / `sut_config` 解析成**本机绝对路径**，
而 `Fingerprint()` 直接 `yaml.Marshal` 整份计划。

**根因**　指纹的语义没被想清楚：它应该刻画**实验条件**（谁、多少人、什么分布、压哪个环境），
而不是**实验产出写到哪个目录**。把输出位置算进去，等于让「在 A 目录跑」和「在 B 目录跑」
变成两个实验。

**修复与验证**　新增 `fingerprintView()`：把这三个路径字段替换成 basename（既抹掉机器差异，
又保留「换了哪个 persona 目录 / 哪份 SUT 配置」这个真正影响结果的信息）。
`TestFingerprintIgnoresMachinePaths` 覆盖 Windows 绝对路径 / Unix 绝对路径 / 相对路径三种写法，
`TestFingerprintSensitiveToSemantics` 反向确认 seed、bot 数、到达率、persona 文件、网关地址变了
指纹必须变。

**面试怎么讲**　「指纹要覆盖实验条件，不能覆盖实验产出位置。这个 bug 不会让任何测试失败，
只会让三个月后的你对着一份复现不出来的实验发呆。」

## F11 · 每次登录遍历整张 session 表

**现象**　账号数上千后，登录耗时随账号数线性上升；3000 个 bot 同时上线时登录被串行化，
`login` 阶段 p99 出现尖刺。

**定位**　旧实现每次登录都遍历整个 `sessions` map，删掉「同账号的」和「已过期的」，
**全程持写锁**。表里有 n 个会话，每次登录就是 O(n)，n 次登录就是 O(n²)，而且全在临界区里。

**根因**　用「全表扫描」实现了一件 O(1) 就能做到的事（让同账号旧 token 失效）。
根子是把「清理」和「失效」两件事混在一个循环里了。

**修复与验证**　加 `accountToken` 索引（账号 → 当前 token），同账号旧 token 失效变成 O(1)；
过期会话改**摊还清理**（表长到阈值才全表扫一次，成本摊到 n 次登录上）。
证据用对照基准跑出来（表内 5000 个其他账号的会话）：

```
BenchmarkLogin-24                300    5261 ns/op    ← 修复后
BenchmarkLoginOldAlgorithm-24    300   67544 ns/op    ← 复刻旧实现的算法
```

12.8 倍，而且旧实现随表长线性变差、新实现基本恒定。

**面试怎么讲**　「先找『每次操作都要做一次全表扫描』。这类问题单机、小数据量下完全看不出来，
等到账号一多就是悬崖——而且它表现为『登录慢』，很容易被误判成 CPU 或 GC 问题。」

## F12 · 协议字段被静默忽略

**现象**　客户端带 `party = [1,2,3]` 请求组队匹配，服务端回 **OK**，然后把它当单人排进了队列。

**定位**　`gateway.dispatch` 里 `protocol.Unmarshal(payload, &req)` 解出了 `EnterQueueReq`，
但后面 `s.enterQueue(st, env.Seq)` 只用了 `env.Seq`——**`req` 从头到尾没被读过一次**。
`Mode` 与 `Party` 两个字段就这样静默消失了。

**根因**　协议先于实现演进：字段加上去了、代码没跟上、也没人报错。
静默忽略是兼容性里最贵的一档——用户以为组队成功了，直到进了房间才发现队友不在。

**修复与验证**　抽出 `CheckQueueRequest(serverMode, req)`：`mode` 必须与服务端一致
（空表示用默认），`party` 只允许空或仅含自己。新增错误码
`mode_unsupported` / `party_unsupported`，拒绝时带上可读原因。
`srv/gateway/queue_test.go` 用 7 个用例钉住，包括「大小写不同不算同一个模式」这种边界。

**面试怎么讲**　「对外暴露的字段只有两种正确结局：实现它，或者明确拒绝它。
静默忽略看起来最省事，实际上是把成本转嫁给了用户。」

## F13 · 32 位平台上的长度前缀溢出

**现象**　（潜在）对端只要发一个 `0xFFFFFFFF` 的长度前缀，32 位构建的进程就会 panic。

**定位**　`if int(total) > r.maxBody+EnvelopeSize` —— `total` 是 `uint32`，
在 32 位平台上 `int(total)` 会变成 **-1**，判断为「没有超限」，紧接着
`make([]byte, int(total)-EnvelopeSize)` 拿到负长度，直接 panic。

**根因**　协议长度字段是无符号语义，却在有符号域里比较。这类问题在 64 位机器上永远测不到。

**修复与验证**　改成 `uint64(total) > uint64(maxBody)+EnvelopeSize`。
`TestFrameLengthMaxUint32` 覆盖极值，并额外覆盖「恰好等于上限」的边界（应当是短帧错误而不是超限）。

**面试怎么讲**　「解析外部输入时，所有长度、偏移都要按无符号语义校验，别中途转 int。
这个 bug 在我的机器上永远不会触发——但它在别人的 32 位构建上就是『四个字节打死进程』。」

## F14 · `DecodeSnapshot` 的注释在说谎

**现象**　注释写着「为热路径省分配，Players 复用调用方传入的底层数组（若容量够）」，
但实测每次调用都分配。

**定位**　实现返回的是 `var m Snapshot`，`m.Players` 永远是 nil，`cap(nil) < n` 恒成立，
所以每次都会 `make`。而且注释说的「调用方传入的」在这条路径上根本不成立——没有入参。

**根因**　两个不同的使用场景被塞进一个函数：一种是**同步消费**（可以复用缓冲），
一种是**把结果塞进 channel 交给别的 goroutine**（必须拥有独立副本，否则下一条会覆盖）。
旧注释描述的是前者，实现做的是后者。

**修复与验证**　拆成两个函数：
`DecodeSnapshot`（明确会分配，因为值会被排队传递）与
`DecodeSnapshotInto(b, dst)`（同步消费时零分配）。
并用 `testing.AllocsPerRun` 把两者钉死：前者 ≥1 次分配，后者在预热后必须 0 次。
热路径（bot 收快照 → channel → 消费）保持分配是**对的**，现在注释不再撒谎。

**面试怎么讲**　「注释和实现不符比慢更危险，因为读代码的人会据此做决定。我把两个语义拆成两个
函数，然后用分配次数的断言把每条语义固定下来。」
